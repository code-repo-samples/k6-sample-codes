# Coke Codes UI Automation

A chained end-to-end Playwright journey through the Coke Codes admin portal:
**Login (SSO/IAP) → Create Program → Edit Program → Create Promotion (mapped to
program) → Create Release → Edit Release → Create Lot → Edit Lot → Create Batch
(organization + promotion from a parameter file) → Trigger code generation →
Create Campaign → Edit Campaign → capture the generated code.**

Plus a separate set of self-contained negative test cases, and a custom
dashboard report on top of Playwright's own reporter.

## 3. Recommended run order

```bash
# 1. Run the chained journey - creates a program, release, lot, batch,
#    triggers code generation, creates a campaign, prints the generated code
npm run test:journey

# 2. Wait ~5-10 minutes for the batch's code generation to fully finish

# 3. Run the independent areas - Validate will pick up the code from step 1
npm run test:other

# 4. Run the negative/error-path tests (any time, order doesn't matter)
npm run test:negative

# Or, to run absolutely everything in one go (accepting that Validate might
# run before code-gen finishes and need a re-run):
npm test

# Either way, build the dashboard afterward:
npm run report:dashboard
```

## 4. First-time setup

```bash
mkdir coke-codes-ui-automation && cd coke-codes-ui-automation
# place all project files into the structure above

npm install
npx playwright install
```

### Configure credentials (.env)
```bash
cp .env.example .env
```
Then edit `.env`:
```
BASE_URL=https://ui-gcp.alpha.codes.coke.com
LOGIN_USERNAME=your-test-account@example.com
LOGIN_PASSWORD=your-test-password
TEST_VALID_CODE=REPLACE_WITH_REAL_UNUSED_CODE
```
`.env` is gitignored — real credentials never get committed. `playwright.config.js`
loads it automatically via `dotenv`, and `LoginPage.loginWithEnvCredentials()`
reads `LOGIN_USERNAME`/`LOGIN_PASSWORD` from it.

### Configure test parameters (test-data/test-config.json)
This is where the **organization ID** and **promotion** used for batch
creation live, along with default program/release/lot/campaign values —
change these without touching any test code:
```json
{
  "batch": {
    "organizationId": "ORG-0001",
    "promotionName": "Promotion01",
    "codesPerFile": 1000
  }
}
```

## 5. Get real selectors before running against the live app

Almost every page object has `// VERIFY:` comments marking guessed selectors —
labels, dropdown names, row/column layout, the code-gen status text, the
container attributes used to scope Lot/Batch panels (`data-release-id`,
`data-lot-id` are placeholders). Record the real ones:

```bash
npm run codegen
```
Click through the actual Create Batch and Campaign screens especially — the
organization/promotion dropdown labels and the "viral code" display element
(`CampaignsPage.getViralCode()`) are the most likely to need correcting.

## 6. Running tests

```bash
npm run test:journey     # runs ONLY the chained e2e journey
npm run test:negative    # runs ONLY the negative/error-path tests
npm run test:other       # runs ONLY Organizations/Validate/Closure Matrix/Queued Requests/GPG Upload
npm test                 # runs everything in tests/

npx playwright test --headed              # watch it run
npx playwright test -g "Create Batch"     # run one stage by name
```

### Why the journey spec is structured differently
`e2e-program-journey.spec.js` uses:
- `test.describe.configure({ mode: 'serial' })` — stages run in a fixed
  order, and if one fails, the rest are skipped rather than cascading into
  confusing unrelated failures.
- **One shared `page`**, opened once in `test.beforeAll` and reused by every
  stage, instead of Playwright's default fresh-page-per-test — because the
  journey is genuinely one continuous session (you can't "restart" halfway
  through and still have the release/lot/batch you created).
- **One shared `journey` object** (module-level) — each stage reads the
  IDs it needs from it and writes back what it generates: `programId` →
  `promotionId` → `releaseId` → `lotId` → `batchId` → `campaignId`/`viralCode`.

Each stage still gets its own `test.describe()` (Login, Create Program, Edit
Program, Create Promotion, Create Release, Edit Release, Create Lot, Edit Lot,
Create Batch, Campaigns) so the dashboard report still breaks results down
per feature area rather than showing one giant blob — see the reporting
section below.

Negative tests deliberately do **not** use this pattern — each opens its own
fresh page via the normal fixture, since they don't depend on journey state
and shouldn't be able to break the chain if one of them fails.

### Why other-pages.spec.js is kept separate, not chained
Organizations, Closure Matrix, Real Time Test, Queued Requests, Download
Codes, and GPG Upload don't depend on the program/release/lot/batch chain at
all. Validate specifically must **not** run immediately after the journey:
the batch code-generation job can take 5–10 minutes to fully finish even
after `waitForCodeGenComplete()` returns, so chaining Validate straight after
would produce flaky "code not found" failures unrelated to any real bug. Run
`other-pages.spec.js` on its own, a few minutes after the journey completes —
its Validate test automatically picks up the most recently generated code
from `test-results/generated-codes.json` if one exists, falling back to
`TEST_VALID_CODE` from `.env` otherwise.

## 7. Where the generated code goes

The last stage of the journey captures the campaign's generated ("viral")
code and:
1. Prints it to the console: `[generated-code] source=campaign programId=... code=...`
2. Appends it to `test-results/generated-codes.json` via `utils/generatedCodesStore.js`
3. Attaches it directly to that test's entry in Playwright's HTML report

This means a later Validate-flow test (or a person testing manually) can read
`test-results/generated-codes.json` to get a real, freshly generated code
instead of a hardcoded placeholder.

## 8. Reports

Same dashboard as before — no changes needed here.

```bash
npm run report              # Playwright's built-in HTML report + trace viewer
npm run report:dashboard    # writes test-results/dashboard-report.html
npm run test:all            # runs tests, then builds the dashboard
```

The dashboard groups by each spec's outermost `test.describe()` — since the
journey keeps one `describe` per stage, "Coverage by Functionality" still
shows granular bars (Create Program, Create Release, Create Batch, Campaigns,
etc.) rather than one lump result, and Positive/Negative coverage still comes
from the `@positive`/`@negative` tags on each test.

## 9. Extending the journey

To add a new stage (e.g. Public Key, Queued Requests) into the chain:
1. Add a method to the relevant page object that returns whatever ID/value
   later stages need.
2. Add a new `test.describe('Stage Name', () => { test('...', { tag: '@positive' }, async () => {...}) })`
   block to `e2e-program-journey.spec.js`, reading/writing the shared `journey` object.
3. If the new stage needs its own parameter (like organization ID or
   promotion), add it to `test-data/test-config.json` rather than hardcoding it.
4. Add a matching negative case to `negative-cases.spec.js` if relevant —
   as its own independent test, not chained into the journey.
